# Accounting Phase 3 Canonical Posting Transition Matrix

Status: evidence-backed transition inventory, 2026-07-29  
Scope: synthetic staging only. This document does not authorize production, Neon, Zoho Books, port 5432, real-data migration, external publication, deployment, commit, or push.

## Boundary

`JournalEntry`, `JournalEntryLine`, and the `GeneralLedgerEntry` projection are Accounting-owned financial facts. Runtime writers must submit a versioned, immutable request to the canonical Accounting posting engine. Seeds and the separately gated historical migration utility are not runtime writers and remain explicit architecture-test exceptions.

The request payload hash is calculated from a deterministic canonical serialization. Replaying the same key and hash returns the same journal; reusing a key with a different hash is a conflict. Posted and submitted facts are immutable. Corrections create a linked reversal and, where required, a replacement.

## Cross-cutting unsafe calculations discovered

- The legacy Accounting service and validators accept JavaScript `number` for journal lines, invoice quantities/rates/tax, payments, payroll, depreciation, recurring entries, partner transactions and job values.
- `SalesInvoiceItem.qty`, `SalesInvoiceItem.exchangeRate`, `PurchaseInvoiceItem.qty`, `TaxLine.taxRate`, `Asset.depreciationRate`, and partner percentage fields are Prisma `Float`.
- Runtime examples include 18% GST, 15-day invoice terms, account names/codes, depreciation assumptions and salary/tax thresholds.
- Report formatting currently converts Decimal facts to `Number`; Phase 3 forbids that for accounting calculations. Read-only UI serialization remains a separate later migration, but all posting, conversion, equality and reconciliation logic must use the shared decimal boundary now.

## Phase 3 rollout sequence

1. Add shared decimal, canonical request, source snapshot, posting-attempt, lineage, approval, numbering and immutable-ledger foundations.
2. Enable canonical posting in synthetic staging and retain legacy reads/drafts.
3. Cut bank transfer, manual journal, CRM invoice request and immutable HRMS payroll request to the canonical boundary.
4. Route every remaining runtime GL/journal writer through the same engine.
5. Install architecture and database protections that reject unapproved writers and mutations.
6. Remove direct-write fallback only after guarded tests prove parity. The historical import and synthetic seed remain explicit non-runtime exceptions.
